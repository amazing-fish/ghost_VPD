# ghost_VPD · Issue 驱动协作规范 v1.0

适用范围：**Issue / PR 协作、证据、隐私与授权要求适用于整个 ghost_VPD 仓库**；设备执行规则按实际工作树分域。默认分支 `main` 目前只有 Legacy 入口 `app/service/vpd/base.py::vpd_task_run()`；`vpdtest` 位于尚未合并的 Skill 开发线（PR #2），统一 `Dispatcher` 位于其上游叠加的 `feat/vpd-goal-loop`（PR #7）。不得把 PR 中的能力当作 `main` 已具备的功能。

核心约束：**Issue 定义任务契约，Agent 负责实现及取证，PR 承载可审查变更，人工负责授权与产品判据确认。**

## 1. 最小协作约定

- **一项 Issue 一个可验收的目标**。可以有多个实施工作包或多个 PR，但范围必须能逐项判断完成与否；不把重构、视觉探索、治理修复和新业务用例无边界混做。
- **Issue 不等于实现方案**。描述行为与约束，允许 Agent 根据证据提出更简单的实现；与原验收条件冲突的方案需先在 Issue 写明并获人工同意。
- **Issue 不等于真机授权**。任意账户变更、收藏、切车、算路都需要当前运行的单次明确授权；车辆运动/车控还必须具备实际监护及符合安全策略的操作条件。
- **不制造通过**。工具成功、产品通过、Agent 自主探索完成、回归可重复四个结论必须分开记录；`pending` 是合格的未知结论，不能为了绿灯确认知识。
- **先读代码再开工**。Issue 中引用的旧事实可已过期。必须校验现有 CLI、知识条目、实际运行代码与设备版本，不因 Issue 写“缺命令”就重复新造。

## 2. 选择 Issue 模板

| 模板 | 典型内容 | 核心验收 |
| --- | --- | --- |
| 工程任务 / 改进 | Goal loop、from-session、Cleanup、知识检索、代码收敛 | 范围明确、回归无退化、有正反例 |
| 缺陷 / 异常 | `target_ambiguous`、`foreground_unknown`、hdc 掉线、疑似产品问题 | 复现环境、首次异常、证据链、正确归因 |
| 知识 / 判据治理 | K-AV/K-QK/K-MOT 条目、Build 差异、产品要求确认 | scope、来源、reviewer、basis、受影响用例 |

Issue 标题建议：`[Task] ...`、`[Bug] ...`、`[Knowledge] ...`。优先级：P0=安全/隐私或严重阻塞，P1=核心链路可靠性，P2=常规能力，P3=整理与体验。优先级不等于真实动作风险等级。

## 3. 状态与职责（不强依赖 GitHub Labels）

1. **Proposed**：创建 Issue，说明目标、已知证据、范围及可验证验收。
2. **Ready**：负责人确认目标和不可越界条件；允许开始离线实现。真机副作用仍须每次运行单独授权。
3. **In Progress**：Agent 以独立分支和 worktree 工作，先记录现有测试基线，再实施最小变更。
4. **Blocked**：缺需求判据、环境或人工授权时记录阻塞与证据，停止越权操作；不是产品 `failed`。
5. **Review**：提交 PR 或本地 diff，附测试证据、风险、遗留问题和复现方法。
6. **Verified → Closed**：验收标准经独立检查满足，必要的真机门槛已满足，由负责人决定合并及关闭。

| 角色 | 责任 | 禁止事项 |
| --- | --- | --- |
| 需求方 / Maintainer（人） | 目标优先级、关键安全授权、产品判据确认、最终验收和合并 | 把“Agent 报告通过”直接当作证据 |
| 实施 Agent | 检索上下文、分析、最小改动、离线测试、受控真机执行、取证、提交交接 | 自行 `confirm` 产品知识；越权车控；绕开所在工作树的设备安全门禁或擅自切换执行入口 |
| Review Agent 或评审人 | 独立验证范围、正确性、安全、隐私和回归兼容 | 只审文字结论不核对证据 |

单人同时担任多个角色时，也要保留**开发者结论与独立验收结果**的逻辑隔离，尤其不能凭单次探索确认产品需求。

## 4. Agent 工作约定

### 开工前（Issue 评论或 PR 说明记录一次即可）

- `git status`、`git worktree list`、HEAD / base SHA，核实本次任务实际执行代码；Skill 任务另核对 Skill 入口、`VPD_WORKSPACE` 和未提交的 Beta 资产，Legacy 任务记录原工程入口与已验证的安全边界。
- 先只读检查 Issue 所称的缺陷是否仍存在；例如 `knowledge resolve` 已有命令，应评估语义缺陷而非重新发明命令。
- 标注风险等级与允许执行的动作。默认只有静态分析与离线测试；真机操作按当次授权与安全规则执行。
- 明确文件/模块的 In、Out，测试方案与预计证据类型；有明显冲突时先记录再做。

### 实施中

- **一个 Agent / 一棵独立 worktree / 一个写入责任主体**，避免多个 Agent 修改相同工作树。可并行审计，但汇总者负责合并冲突。
- 遵守 stacked PR：标明 `base` 与上游 PR，不能因为多个 PR 都未合并而直接改 `main`。禁止未经许可 `reset --hard`、`clean -fd`、force-push、历史重写或直接合并。
- **选择真实存在且符合任务范围的执行入口**：`main` 的原工程入口是 `app/service/vpd/base.py::vpd_task_run()`，并非 `vpdtest` 或 Dispatcher。它属于独立 Legacy 链路，不得假定具备新 Skill 的权限、重检、留证与运动看门狗能力。Legacy 真机任务须先审计实际安全保护、明确本次授权与监护条件；没有可验证的安全边界时停止自动执行，不能为满足 Issue 直接调用驱动/HDC。
- **Skill 工作树**：设备动作必须走该版本实际存在的 `vpdtest` 受控入口；凡依赖统一 Dispatcher 的任务，须先核对当前代码确实包含该模块并经过相应安全测试。不得绕过 policy/Dispatcher 直接调用 HDC/uitest；如果当前工作树缺少所要求的安全组件，改用经授权且具备组件的工作树，或报告 `blocked`，**绝不自动降级到 Legacy 直连路径**。
- 人工 Console 操作必须作为独立手工行为记录，不能算 Agent 自主动作证据。
- 保护原始 `runs` 证据；不对失败事件做静默删除。`effect_unknown` 不能当作未下发。截图与 UI 树遵守隐私门禁；完整 VIN、手机号、口令等不得写入 Issue、PR、仓库和日志。
- 代码/配置修改后优先加正反向测试；不要只修改 fixture 或断言来掩盖知识 confirmed/unconfirmed 状态漂移。
- 无需为每一次简单动作刷 Issue 评论。只在关键阶段、阻塞、范围调整、验收结果变化时更新。

### 阶段交接（Issue 评论或 PR）

用以下**固定六项**汇报：

1. **基线**：worktree、branch、base SHA、HEAD SHA、workspace、设备 APP build（如有）。
2. **变更**：改了什么、为什么、明确没改什么，文件与 diff。
3. **验证**：基线测试 / 新测试结果；`real_device` 和 `offline_replay` 分开；真实 `run_id/obs_id`。
4. **判定**：操作是否成功、产品 verdict（passed/failed/pending/blocked）、oracle_refs、适用范围。
5. **清理与安全**：副作用是否授权、Safety Hold 状态、Cleanup 是否有独立后置验证。
6. **后续**：阻塞、未完成事项、需人工决策、建议后续 Issue/PR。

## 5. 证据层级及验收口径

| 级别 | 证据 | 可以声明 | 不可声明 |
| --- | --- | --- | --- |
| E0 | 静态审计 / 代码阅读 | 实现存在、接口设计分析 | 真机可用 |
| E1 | pytest / replay world | 协议与模拟世界下逻辑通过 | 产品行为已符合要求 |
| E2 | 真机 observe/act/run、APP build、run_id | 当前设备/版本操作表现 | 稳定跨设备泛化 |
| E3 | 相同内容哈希下独立真机重放 + Cleanup 后置核验 | 在已测试环境中具备复测证据 | 没有确认 Oracle 也算产品 passed |

- **成功判定**：设备动作下发成功不等于达到后置条件；后置条件成立不等于有 confirmed 且适用的产品判据。
- **Cleanup**：严格区分 `attempted` / `executed` / `verified`。若关键清理未独立验证，不得声称环境已恢复。
- **故障归因**：区分工具、环境、产品、需求未确认。USB 物理断链不归因于 APP；未知前台不推断为 Launcher。
- **用例成熟度**：候选用例可以生成并 lint 通过，但正式回归需遵循实际晋级门槛（独立重放、判据、清理、人工评审）。

## 6. Issue、PR 与验收的关联

- 每个 PR 必须引用 Issue 并说明 `base`、head SHA、测试基线与风险。只修一个子目标时写 `Refs #9`，**不要提前 `Closes #9`**。
- 只有 Issue 的全部验收条款满足且可追溯时，才能写 `Closes #N` 并由维护者关闭。可通过多个相互独立的 PR 完成一个 Issue；每个 PR 仍需独立可审查。
- 产品判据 `confirm` 和敏感数据历史重写是单独的人工治理决策，不因为 Issue/PR 获批便自动执行。
- 对 Issue #9 这种包含多个问题的任务，拆分实际 PR 工作包优于扩展为一个不可审查的大型 PR；在 Issue 顶部维护完成与待完成清单。

## 7. 运行与安装注意

- **Issue Forms 只有合入默认分支 `main` 后，才会在 GitHub 新建 Issue 的选择界面生效**；仅放在开发分支不能启用。
- 表单 `required` 是输入提示/校验机制；仓库为私有时不应仅依赖 UI 校验，仍需按本规范人工/Agent 审查缺失字段。
- `.github/ISSUE_TEMPLATE/config.yml` 默认禁用空白 Issue，是为了避免绕开核心信息；紧急情况使用“缺陷 / 异常”，安全问题先处理现场再补 Issue。
- PR 模板在 `.github/PULL_REQUEST_TEMPLATE.md`，用于将任务目标、证据和遗留风险对齐。
