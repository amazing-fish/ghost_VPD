# 资产升降级：保留证据，分别处理成熟度、审核和结论

## 本次可以决定什么

建议接受“显式撤销资产审核”这一独立切片。它补上已有 approve 的反向入口，避免只能删字段或手改 status。
**它不把失败用例降级，不自动确认产品规则，也不改写任何生产资产。**

| 维度 | 回答的问题 | 当前实现 |
| --- | --- | --- |
| 成熟度 status | 资产曾走到哪一阶段 | draft / exploration_record → candidate → replay_verified → regression |
| 人审当前是否有效 | 这份资产现在是否获准复用 | approved / stale / pending / not_required / **revoked** |
| 产品结论与证据 | 这次在什么条件下证明了什么 | 当前运行的 verdict、Oracle、事实、run/obs 和独立 Cleanup |
| 覆盖 | 哪条原始要求的哪些分支已验收 | 独立逐例验收；文件数量、成熟度或动作成功不代替业务覆盖 |

“已到 regression”不是跨版本、跨园区永久有效；“稳定复现失败”也不意味着资产不成熟。
稳定失败沿既有 known_failure + 缺陷引用，保留原预期，不为变绿改断言。

## 已实现：撤销审核，再由人重新审查

在 vpd_skill 目录：

- 撤销：python -m vpdtest case revoke-review CASE_ID --reviewer "实际作出撤销决定的人" --basis "撤销原因及证据链接"
- 查看：python -m vpdtest case review CASE_ID
- 只读盘点：python -m vpdtest case readiness CASE_ID
- 重新启用：完整核对当前资产和所绑定配置后，由人明确确认，再执行现有 case approve --reviewer --basis。

**撤销范围是单个资产已有的审核，不是知识确认、设备授权或某次原始运行证据。**

1. 保留原批准人、依据、时间、绑定和引擎快照；在 asset_review.revocation 记录撤销人、依据、带时区时间，并追加 asset_review_revoked 历史事件及原批准绑定。
2. 成熟度、product_status、replays、原始 run/obs 和知识文件保持。即使当前配置损坏或审核已 stale，也能撤销完整的既有批准，无需先让用例可运行。
3. 晋级、suite、experience validate 批量路径及每条 runner 的批量复检拒绝撤销资产；预检在创建运行/设备之前。单条诊断仍可取证，但明确 informal，不自动复用或恢复批准。
4. 非探索来源也适用。发生过撤销后，后续复用持续要求有效审核；删除当前 record、恢复旧批准记录或只改 status 不能抹掉仍留存的撤销历史。
5. 重新 approve 要求现有 lint 及显式审核输入。只有撤销事件之后、与当前批准相匹配的新批准事件，才能解除撤销；旧撤销记录仍保留。重复撤销拒绝，防止覆盖第一次依据。
6. 明确的 revocation 字段即使损坏，也不恢复有效性。没有完整既有批准时拒绝撤销，不创建“假批准”。

这是本地审计机制，不认证 reviewer 身份，也不防止有文件写权限的人蓄意改写完整记录与历史。
审核、撤销、晋级、记录重放四个入口共享按用例的跨进程更新锁，复用现有 OS 文件锁实现；
拿锁后重读当前文件，避免旧快照把已完成的撤销覆盖回去。只读预检不创建锁文件；
修改入口即使最后拒绝，也可能在工作区内留下协调锁文件，但不改动资产或证据。
新建用例使用独占创建，已存在文件不能被同名并发创建覆盖。外部直接编辑仍须遵守单写入人约定。

**撤销不是紧急停止。** 它在下一次入口/批量逐例检查生效，不中断已经在执行的设备动作；现场安全继续走既有停止、看门狗与人工接管。
本次未启用设备、未执行任何生产 revoke / approve / confirm。

## 后续机制：推荐取舍，尚未实现

| 事项 | 推荐做法 | 不采用的做法 |
| --- | --- | --- |
| 审核失效 | 自动计算 stale 并拒绝受审核约束的复用；保留原声明成熟度和失败原因 | 每次引擎变化都把所有 case 写回 draft |
| 显式降级 | 后续独立增加只向低阶段移动的命令，记录操作者、依据、原阶段与目标阶段；不清空历史 | 修改 status 就声称旧证据无效，或删除失败重放 |
| 无效证据撤回 | 后续按具体 run/断言、受影响 scope、理由登记排除项；晋级计算排除该证据，原件保留 | 用撤销审核替代证据撤回，或把全库历史一并作废 |
| 恢复等级 | 当前定义重新通过原晋级门槛；被明确排除的证据不能自动复活 | approve 一次直接恢复 regression 或业务覆盖 |
| 正式资格持续核验 | 后续保存晋级当时的必要选项及依据，再设计当前资格检查；历史缺项如实标未知 | 从 status 推断已满足当前全部证据与实机范围 |

以上是后续设计建议，不是本次已交付的命令或新强制规范。当前原生 readiness 已提供晋级预检与重放资格，
但它不是原始证据包验收，也不会对 regression 自动重新执行一遍全套准入判断。

## 作用域与冲突：沿现有证据链，不靠次数投票

- 现有知识 applies_to 与运行时独立事实决定适用性。缺失或无法比较为 unknown，不等于明确不适用；
  业务 --env 声明不能冒充当前车辆/账号/园区事实。
- 记录源代码/内容/依赖/审核绑定、APP build、设备形态及真实 run/obs。涉及实体、账号、园区的结论，
  必须说明已证范围；哪些业务事实已能独立采集，沿 provider 契约，不能凭记录一段说明就视为实现。
- 同一 subject 且作用域重叠的不同 expected 沿现有 conflict 路径保持 pending；不同 build 的独立口径不互相覆盖。
  不采用“最新一条获胜”或“观察两次就自动 confirmed”。
- 工作机 2026-11-06 的例子：词×电梯口组合只在由度金闽园有证据，金桥充电桩分支被策略拒绝；
  不能外推。D011 / D010 差异只命中一个对象，不能用名称合并实体，也不能在真值未裁定时重写编号预期。
- 对已确认规则的怀疑，先保存矛盾证据与适用范围，由实际负责人裁决；工程批准和 PR 合入不代替产品确认。

## 验收与剩余决策

本次验收看三件事：原批准和历史是否完整保留；撤销资产是否在所有已有批量入口前被拒绝；
重新批准是否仍走原审核/判据/动作授权边界。合成测试与离线 CI 属 E1，不宣称实机或产品通过。

需要负责人后续裁定的是具体产品契约和资产复用依据，不需要再批准本片的每一次测试。
显式降级、证据排除和跨 scope 资格重算应分别交付；尤其先明确历史离线豁免的可追溯方式，
再扩大运行时“正式资格”的含义。不会为了凑齐一套状态机同时改动这些门禁。
