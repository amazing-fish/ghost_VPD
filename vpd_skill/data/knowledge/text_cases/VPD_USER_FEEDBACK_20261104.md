## MAN-QK-COMB-001 · 构造收藏后验证文字与标签组合

### 场景与依据

工作机曾报告B1单独返回两条车位，B1＋电梯口为空，空词＋电梯口有五条结果；这段组合现象缺原始图与独立交集数据。
TC-QK-242 v6有空查询单标签和本轮标签清理模式，不能替代本用例，也不扩大其已有裁定。
Owner：[搜索业务#80](https://github.com/amazing-fish/ghost_VPD/issues/80)，真实收藏来源与消费者沿#111。

### 受控数据与写前检查

1. 记录run、APP/build、设备形态、当前账户标识、车辆和园区；未知身份不当成同一个环境。
2. 从独立收藏入口读取现有完整集合、容量和实体身份；地图“常去地点”混合卡或搜索结果不作为完整收藏来源。
3. 至少准备下表三类**不同物理实体**。使用本轮唯一非敏感名称前缀；名称不能当唯一实体键。
   关键词建议使用本轮名称前缀，避免把尚未裁定的楼层实体范围或编号必显混入本场景。
4. 已有收藏不得删除、改名或占用来凑数据。容量不足、候选实体不足或原始标签状态不明确时保留blocked/pending及现场证据。
5. 收藏和标签写入经本次`user_data`授权与Dispatcher，提交不盲目重试。每次可能下发即记run所有权、实体ID和基线。

| 受控实体 | 收藏名匹配关键词 | 真实标签匹配 | 独立读回必须证明 |
|---|---|---|---|
| A | 是 | 是 | 同园区/楼层/类型/实体ID，保存后的名称与标签 |
| B | 是 | 否 | 同样的身份，目标标签确为未选，不能用“树没搜到”推断 |
| C | 否 | 是 | 同样的身份，与A/B不同，名称不匹配、目标标签已选 |

数据写入后退出并重新打开独立收藏/实体详情，读取A/B/C和原有集合。
创建动作返回成功、同屏出现三个名字或查询结果本身，都不能替代这次读回。未完成读回不进入组合结论。

### 执行与证据

- 分别测试：仅关键词、空关键词仅标签、先关键词后标签、先标签后关键词、取消标签后保持/恢复关键词。
- 每个分支单独记录实际SearchField值（含originalText冲突）、标签选中/未选状态、请求/加载终态、完整结果集合及同一行实体归属。
- 保存操作前后原图、原树、动作记录、run/obs与清理；Toast如出现则绑定触发动作采帧，不能靠固定等待证明查询完成。
- 既有`qk_tag_elevator`只校准过空查询结构；不要为了非空查询放宽它。非空时真实接收者、收藏创建/完整列表入口未有合格来源时，先以受控会话校准，再固化可执行case。

### 判定与需要用户判断的内容

先验证三类数据和每个输入/选中态，随后把结果按实体ID列出来。以下只是可区分的候选规则，不是已确认预期：

| 待裁定规则 | 三类实体在组合分支中的预期差别 |
|---|---|
| 文字与标签同时满足 | A；B/C排除 |
| 选择标签替代文字 | A/C；还需界面实际清空文字或明确切模式 |
| 两种模式互斥 | 依明确的禁用、提示或模式切换契约验收 |

现有集合之外的实体也要保留，不为贴合这张表过滤现场结果。请求终态、完整集合或身份不充分仍待确认。
不要因A出现就宣布交集规则通过，不因空白就宣布不支持组合。带原图/缺图记录将实际差异交用户判断。

### 清理与退出条件

只撤回本轮实际新增且身份可核的A/B/C收藏与标签；可能下发但效果未知时先查当前数据再补偿，不重复点击开关。
复用242的写前基线及`after_dispatch`归属思路，但不能把固定A207选择器套到任意实体。
独立重开收藏/实体详情，证明本轮新增项已撤回、原有集合和标签未变。清理未知/失败单独报告，不称环境已恢复。
现场取证、可执行case、资产人审、产品判据及正式覆盖分别记账；尚未完成前不放进批量回归入口。

## 反馈场景共用契约

原始要求包含三个层次：**用户可理解的操作状态提示、手机日志上传云端、车辆上电后车端日志上传DDI**。
Toast只是第一层的观察，不能用来证明后两层完成；“未在树中出现”或“截图没拍到”也不能证明没有Toast。

### 触发和提示证据

提交前先记录非敏感关联标记、实际内容/页面、手机与车辆上下文、独立网络事实和时间。
使用当前真实接收者，通过`vpdtest act tap ... --capture-transient 3`或tap步骤的`capture_transient`开启采集；
3秒只是采集预算，不是产品提示时长、上传SLA或“无日志”期限。需要调整时保留参数和实际帧间隙。
先取得首帧，再走现有定位/授权/新鲜度/Dispatcher复核；帧源不就绪不提交。提交只发一次，采集失败不自动重发。
保留baseline、触发时间/发送回执、触发后帧、完整SHA256、丢帧/错误、实际采集间隙及末次前台。
记录图片中**实际文案、类型和用户可理解的含义**；不强制所有版本都出现“感谢您的宝贵建议”。

`transient_text_seen`仅在同触发、同动作epoch、当前APP且新鲜的完整原树取得肯定文字时支持出现事实；
它读取完整可见文本而非texts前60条。只在画面里的提示需查帧，由视觉/人工给建议；未形成确定性文字证据时仍不可判定。
单纯没命中不能判“无提示”，负向预期也不会因此通过。明确帧源错误按取证异常处理；静止帧、漏帧与未识别分别保留。
旧`monitor`/`text_seen`继续用于各自普通时间窗，不能替代这条触发绑定的短提示证据。

### 实际日志证据与结论

云端与DDI分别记录查询权限、系统/接口、查询时间窗和终态、反馈关联ID、车辆/账户/版本、事件时间、接收时间及原始回执。
没有查询权限、查不到对应接口、只查了无关联条件、传输尚未终结、缺上电前提或网络事实，均记**未验证/未知**，不记无日志。
任意等几秒或几分钟后未搜到不构成不存在证据；按实际产品时限/任务终态及权威完整查询判定，时限未定则待补。
DDI分支等有授权的车辆上电事件并记录独立事实，不为本用例自行上电、移车或切账户。

| 提示观察 | 实际日志证据 | 处理 |
|---|---|---|
| 用户理解为已完成 | 关联日志已接收 | 分层记录；仍分别核手机云端与车端DDI，不扩大为全链路通过 |
| 用户理解为已完成 | 权威、完整、匹配前提与终态的查询确认缺失/明确拒绝 | 记录提示与事实矛盾的产品问题候选，保留原图、回执与用户原则；按适用判据办理正式判定 |
| 用户理解为已完成 | 权限不足、查询未终结、延迟或其它未知 | 实际上传未验证，先调查；不能宣称有日志或无日志 |
| 独立确认断网 | 明确失败/离线/待上传等真实状态 | 检查用户是否被正确告知当前状态；具体措辞与补传策略不从旧Toast推断 |
| 提示未捕获 | 任意 | 提示检查不可判定或取证异常；日志检查独立继续，不宣称无提示 |

## MAN-QK-FEEDBACK-001 · 正常联网提交与分层回执

前置：当前服务和网络有独立可用证据；查询权限明确。操作：一次反馈提交并绑定采帧，记录用户理解，关联手机云端回执；
有真实且授权的上电事件时再查车端DDI。验收：按共用表分别判各层，保留权威缺失问题候选，不能把Toast当上传成功。
退出：提交是实际外部写入，保留测试标记及数据，不擅自删除后台/车端日志；没有授权的查询分支保持未验证。

## MAN-QK-FEEDBACK-002 · 已确认断网时的真实提示

前置：经现场允许的方法独立证明手机断网，记录切网前状态与恢复责任；不能仅凭APP错误文案或--env自证断网。
操作：一次提交、采集提示及本地/服务响应。验收：如误导用户认为已完成但权威证据确认未完成，登记问题；
正确失败或明确排队状态按实际语义记录。离线时无法查询后台不等于无日志。退出：按原状态恢复网络并独立核验。

## MAN-QK-FEEDBACK-003 · 延迟上传

前置：可关联的提交与独立上传状态，允许的观察时限/终态来源明确。操作：提交一次，记录提示与多次合法回执查询。
验收：记录发生与接收时间差；在权威终态前保持pending，不能因任意等待宣称缺日志。若有正式SLA再测边界。
退出：保留原提交和最终回执，不重新提交来制造“上传成功”。

## MAN-QK-FEEDBACK-004 · 恢复网络后的补传

前置：复用002独立确认的离线提交及本地接收/排队事实；不先假定系统支持离线排队。
操作：恢复到已验证可用网络，保持原关联ID，观察自动补传或明确重试入口及新提示。
验收：区分未保留、仍待传、已补传与未知；先核既定策略，未定义时收集差异等待裁定。重启后恢复不代替该路径。
退出：恢复网络基线，记录是否仍有待传项及其归属，不删除不属于本轮的数据。

## MAN-QK-FEEDBACK-005 · 显式重复提交

前置：允许的重复/幂等产品规则或明确待决状态，服务可查询且本轮记录可区分。
操作：测试者有意触发两次，每次独立采集窗口和动作回执，记录关联ID/幂等键；执行器自身不自动重试。
验收：分别查询手机云端、适用的车端DDI，记录一条/多条、关联关系和时间；按正式重复策略判断，规则未知时不擅自要求恰好一条。
退出：如实保留两次请求及回执；不能丢掉第一次失败或以第二次成功改判第一次。
